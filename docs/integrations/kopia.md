# Kopia Read-Only Protection Visibility

## Purpose

GoreeCloud Manager exposes native Kopia protection state without receiving Kopia repository credentials, SFTP credentials, SSH keys, Docker control, or direct repository access.

Kopia remains authoritative for snapshots, repository state, retention, maintenance, verification, and restore operations. Manager consumes only a small sanitized JSON status artifact generated by a delegated host-side collector.

This integration is distinct from the `GoreeCloud Kopia Backup` Healthchecks check:

- **Healthchecks** reports whether the scheduled backup heartbeat is current.
- **Native Kopia visibility** reports the latest known snapshot/protection state collected from Kopia itself.
- **Restore readiness** remains a separate recovery validation concern and is not inferred from either signal.

## Live GoreeCloud Boundary

The current Kopia deployment on `goreecloud-vps-01` is an on-demand CLI container using the pinned `kopia/kopia:0.23.1` image. Its encrypted repository is reached over SFTP/NetBird and its protected repository configuration, password, SSH private key, and known-hosts material remain outside GoreeCloud Manager.

Manager must never receive:

- `/var/run/docker.sock`
- `/srv/docker/secrets/kopia`
- the Kopia repository password
- the Kopia repository configuration
- SFTP private keys
- known-hosts material
- arbitrary shell execution authority
- snapshot create/delete/retention/maintenance/restore authority

## Delegated Collector

`ops/kopia-status-collector.py` is the approved host-side collector implementation.

The deployment copies that script into the Kopia stack and calls it from the existing root-owned backup wrapper. The collector may execute the existing pinned Kopia Compose service to perform this read-only query after a successful snapshot:

```text
kopia snapshot list /source --json --max-results=1
```

The collector never returns raw Kopia configuration to Manager. It explicitly normalizes only approved fields and writes the result atomically.

When a scheduled backup is skipped because the laptop target is unavailable, or when snapshot creation fails, the collector writes the new attempt state while preserving the last known successful snapshot from the previous artifact. This prevents Manager from confusing "repository unavailable now" with "no known successful snapshot."

Collector failure must not change the backup result. The wrapper logs a warning if the Manager status artifact cannot be refreshed, while Kopia and Healthchecks continue to retain their existing authority and exit-code behavior.

## Artifact Location and Permissions

Host path:

```text
/srv/docker/appdata/goreecloud-manager/integrations/kopia/status.json
```

Container path:

```text
/app/integrations/kopia/status.json
```

The host directory is root-owned and contains only sanitized non-secret integration data. The collector writes `status.json` atomically with mode `0644`. Manager receives only the containing directory through a read-only bind mount.

The Manager container does not mount the Kopia stack, Kopia appdata, repository configuration, or Kopia secrets.

## Artifact Schema v1

```json
{
  "schema_version": 1,
  "generated_at": "2026-08-11T13:00:00Z",
  "source": {
    "host": "goreecloud-vps-01",
    "label": "GoreeCloud VPS protected data"
  },
  "repository_query": {
    "state": "ok",
    "checked_at": "2026-08-11T13:00:00Z"
  },
  "latest_attempt": {
    "state": "success",
    "at": "2026-08-11T03:33:30Z",
    "reason": "snapshot-created"
  },
  "latest_snapshot": {
    "id": "example-snapshot-id",
    "start_time": "2026-08-11T03:33:28Z",
    "end_time": "2026-08-11T03:33:30Z",
    "description": "Scheduled GoreeCloud VPS backup to laptop SFTP repository",
    "size_bytes": 484991682,
    "file_count": 1507,
    "directory_count": 207,
    "error_count": 0,
    "retention_reasons": [
      "latest-1",
      "daily-1"
    ]
  }
}
```

### Field Sources

For Kopia 0.23.1 snapshot-list JSON:

- `latest_snapshot.id` comes from snapshot `id`.
- start/end time come from `startTime` / `endTime`.
- description comes from `description`.
- protected size comes from `rootEntry.summ.size` with `stats.totalSize` only as a compatibility fallback.
- total file count comes from `rootEntry.summ.files`.
- total directory count comes from `rootEntry.summ.dirs`.
- snapshot error count comes from `rootEntry.summ.numFailed` with `stats.errorCount` only as a compatibility fallback.
- retention reasons come from `retentionReason`.

The collector intentionally does not export `source.userName`, repository location, SFTP endpoint, root object ID, cache statistics, protected secret paths, or raw command output.

## Attempt States

Supported attempt states:

- `success` — a snapshot was successfully created and the collector was invoked for that result.
- `skipped` — the scheduled wrapper deliberately did not run Kopia, for example because the laptop target was unavailable or another run already held the lock.
- `failed` — Kopia snapshot creation returned a non-zero result.
- `unknown` — bootstrap or incomplete status where the last attempt cannot yet be established.

Known normalized reasons include:

- `snapshot-created`
- `snapshot-observed`
- `target-unavailable`
- `snapshot-failed`
- `concurrent-run`
- `bootstrap`

## Repository Query States

- `ok` — the collector successfully queried Kopia snapshot JSON during this artifact refresh.
- `not_attempted` — the current artifact update did not query the repository, normally because the backup was skipped or failed before a refresh was appropriate.
- `unavailable` — reserved for a normalized collector result where the repository was known unavailable.
- `error` — the collector attempted the read-only query and it failed.

Raw subprocess stderr is not placed in the artifact.

## Manager Configuration

```dotenv
KOPIA_ENABLED=true
KOPIA_STATUS_HOST_DIR=/srv/docker/appdata/goreecloud-manager/integrations/kopia
KOPIA_STATUS_PATH=/app/integrations/kopia/status.json
KOPIA_STATUS_MAX_AGE_SECONDS=28800
KOPIA_SNAPSHOT_MAX_AGE_SECONDS=43200
```

The eight-hour artifact freshness window is intentionally larger than the six-hour backup cadence plus randomized timer delay. The twelve-hour snapshot freshness window allows one missed/skipped six-hour run before age alone becomes an additional degraded condition.

## Manager Runtime States

Manager fails soft:

- `disabled` — Kopia native visibility is not enabled.
- `misconfigured` — the status artifact path is empty.
- `unavailable` — the artifact is missing, unreadable, malformed, or uses an unsupported schema.
- `degraded` — valid artifact data exists but the artifact is stale, the latest attempt was skipped/failed/unknown, the repository query failed, the snapshot reports errors, no snapshot is recorded, or the snapshot exceeds the configured freshness window.
- `healthy` — valid fresh artifact data exists, the latest attempt succeeded, the latest snapshot is within the configured freshness window, and the snapshot reports no errors.

A degraded or unavailable Kopia integration must not break the Overview or `/healthz/` endpoint.

## UI Contract

The Overview presents native Kopia status separately from Healthchecks. It may display:

- latest attempt state, normalized reason, and time
- repository-query state
- artifact update time and age
- latest snapshot ID
- snapshot start/end time
- snapshot age
- protected size
- total files and directories
- snapshot error count
- retention reasons

All timestamps use the application `America/Chicago` timezone and 12-hour formatting.

The UI must state that recent snapshot visibility does not prove restore readiness.
